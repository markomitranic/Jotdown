A sidebar with sixty rows in it is a sidebar nobody reads. This site splits its
pages into **sections**, each with a sidebar of its own, and puts a dropdown
above the tree so you can step between them. This site has four: the Guide,
How it works, which you are reading now, the Decision records and the
Examples. Open the switcher at the top of the sidebar and you see all four,
whichever one you are standing in.

The point is that a reader inside the Examples sees the Examples and nothing
else, not those plus every guide and every decision ever recorded. The cost is one line in a
`meta.json` and one colour in the project's theme.

## Adding one

Three files and an Overview page, no code. `docs/api/` is the worked example
here; the chapters after it explain what each line is doing.

<Steps>

<Step>

**Declare the folder.** Create `docs/api/meta.json`:

```json title="docs/api/meta.json"
{
  "title": "API reference",
  "icon": "Plug",
  "description": "Endpoints, in detail",
  "root": true,
  "pages": ["index", "authentication", "endpoints", "..."]
}
```

`title`, `icon` and `description` are the switcher row: the name, the boxed
[Lucide](https://lucide.dev/icons/) glyph, and the line under the name. Keep the
description near thirty characters, because the row is one line and cuts the
rest with an ellipsis. Name the folder what `title` says, lowercase and
hyphenated, since the folder name is the section's URL. `"index"` comes first in
`pages` because a section's first row is its Overview, which a chapter below is
about.

</Step>

<Step>

**Write its Overview**, `docs/api/index.mdx`, titled `Overview` in its front
matter, with a `description` and a `<DocCardList />`. The description is printed
under the title for you, so there is no lead paragraph to write. Same shape as
[this section's own Overview](./index.mdx).

</Step>

<Step>

**Hold it out of the tree above it**, in `docs/meta.json`. The `!` is what
stops the section's pages from also filling Documentation's sidebar, which is
the duplication the split was for:

```json title="docs/meta.json"
{
  "title": "Documentation",
  "description": "Everything this site documents",
  "pages": ["index", "decision-records", "!manual", "!api", "..."]
}
```

The switcher lists the sections in the order their `!` lines come in, so this
one puts the manual above the API.

</Step>

<Step>

**Give it a colour** in the `sections` of the project's theme, by naming one of
its tokens:

```json title=".jotdown/config.json"
{
  "theme": {
    "sections": { "api": "chart-2" }
  }
}
```

A token has a value in each mode, so one line colours the section in both. The
key is the folder's name, and a section without one falls back to `primary`, so
this step is optional and nothing breaks if you skip it. Pick the token as if it
were text, not decoration: the current sidebar row is 13px type in that colour,
so the chart colour you point at should clear 4.5:1 against the sidebar in both
modes. [Branding](../studio/branding.mdx) is where the chart
colours themselves are set.

</Step>

</Steps>

## A section is a folder that says so

Fumadocs calls it a **root folder**: a folder whose `meta.json` carries
`"root": true`. Stand anywhere inside it and the sidebar narrows to that folder.
`docs/how-it-works/` is one, so `/how-it-works/configuration` shows you this
manual's rows instead of the whole site.

`docs/` is a section too, and it is the odd one. There is no folder above
`docs/` to put a `"root": true` into, so nothing declares it. But the sidebar you
see at `/` still has to belong to *some* section, or the switcher would have one
row and nothing to switch to. So `packages/core/lib/sections.tsx` treats the whole tree as a
section and reads its name and blurb out of `docs/meta.json`:

```json title="docs/meta.json"
{
  "title": "Documentation",
  "description": "Everything this site documents",
  "pages": ["index", "decision-records", "!manual", "..."]
}
```

That `title` is the word on the switcher row. The one thing `docs/meta.json`
cannot carry is an icon, because Fumadocs' type for the whole tree has no icon
field, so the Documentation row borrows the `icon` from `docs/index.mdx`
instead. Every other section has its icon in its own `meta.json` beside its
title.

Three things make a section, and they live in three different files:

| What | Where | Doing what |
| --- | --- | --- |
| `"root": true` | the folder's `meta.json` | gives the folder its own sidebar |
| `"!<folder>"` | `docs/meta.json` | holds it out of the sidebar above it |
| `"<folder>": "chart-2"` | the `sections` of the theme in `.jotdown/config.json` | the colour of its icon and its current row |

Two of those three spell the folder out, and the switcher row shows `title`
instead, which is how a folder and its label drift apart: rename the label a
couple of times and the folder ends up naming something the pages stopped being
about. Renaming the folder too is a three-place edit. Move the folder, then fix
the `!<folder>` line and its key in the theme's `sections` by hand, and fix the
links `bun run check:links` lists. The old URLs stop working. If you shared
them, add `moved.json` entries to forward them.

Changing an existing section is those same three files. Documentation is the
exception, with its name and blurb in `docs/meta.json` and its icon in
`docs/index.mdx`.

Exclusion is not deletion. Fumadocs parks a folder left out of its parent's
`pages` in a second tree of its own, so its pages still build, still turn up in
search and still scope correctly. Leave that line out and everything still
works, except for the duplicated pages step three was about.

`packages/core/lib/sections.tsx` builds the switcher rows from the page tree, so a new section
needs no code at all. It binds each row to a set of URLs rather than to a
folder, which is the one thing Fumadocs does differently out of the box: bound
to folders, a row only appears while you are standing in a section beside it,
and the Documentation row could never exist.

## What sections are good for

A section is worth it when a reader lives inside it for a while and the pages
around it are noise to them. Some shapes that fit:

- **A generated reference.** Hundreds of pages a script writes from code,
  which would otherwise be most of the sidebar.
- **On-call runbooks.** Read at 3am, with no patience for anything else on
  screen.
- **Decision records.** Dozens of numbered pages, read when you are about to
  reverse one.
- **A second audience.** A public guide to a side project, living in the same
  repo as your own notes on it.
- **Last year's release.** `"root"` also takes a string, and root folders sharing
  that string are treated as interchangeable versions of each other: the
  switcher then lands you on the same page in the other version.

And when not to. A section hides its neighbours, so anything a reader moves
in and out of while doing one task should stay an ordinary folder in the tree.
Four sections is a navigation; twelve is a filing cabinet.


## Every section opens with an Overview

The first row of every sidebar on this site is a page titled **Overview**, and
it is the same file in every section: the folder's `index.mdx`, listed first in
`pages`. The Guide's is `docs/index.mdx`, served at `/`. How it works' is
`docs/how-it-works/index.mdx`, served at `/how-it-works`.

That row is where a reader who has just arrived in a section finds out what the
section is for, so write it as an introduction to the ideas the other rows
assume, then end it with `<DocCardList />`. The switcher row above it already
says which section you are in, which is why the page itself is called Overview
and not the section's name again.

The reason this needs writing down is that Fumadocs will not do it for you. An
ordinary folder picks up its own `index.mdx` as a landing page automatically. A
folder with `"root": true` does not, and here is the line in `fumadocs-core`
that says so:

```js
} else if (!isRoot) {
  const defaultPath = resolveFlattenPath(joinPath(folderPath, "index"), "page");
```

So a section has to be told about its own landing page, and there are two ways
to do it. Listing `"index"` in `pages` is the one we use: the page becomes an
ordinary row, and `packages/core/lib/sections.tsx` points the switcher row at the first page
in the section, which is that row. The other is `"pagesIndex": "index"`, which
binds the page to the switcher row and takes it out of the tree.

| In the folder | What you get |
| --- | --- |
| `"index"` first in `pages` | An Overview row at the top of the sidebar. This is the convention. |
| `"pagesIndex": "index"` | The switcher row opens it, but nothing in the sidebar names it, so the section looks like it has no front page. |
| both | Fumadocs drops the index and keeps the row, so the two cancel out. Do not write both. |
| neither | The switcher row opens whichever page happens to be first. |

This site's old Docs manual section used `pagesIndex` for a while, and the symptom was a sidebar
starting at Browser editor with nothing above it, while `/manual` loaded
perfectly well if you typed the address.

## What a section costs you

Two rough edges, both small and both worth knowing before you add a fifth
section.

The [browser arranger](./browser-editor.mdx) only ever sees the section you are
standing in, so a page cannot be dragged from one section into another. Moving
one across means moving the file and editing both `meta.json` files by hand.

The accent follows the first segment of the URL, which is usually a section but
does not have to be. Name `guides` in the theme's `sections` and the tree tints
inside `/guides/*` even though that folder is an ordinary one and the switcher
still says Guide. Useful if you want a colour per top-level
folder, confusing if you did not mean it.
