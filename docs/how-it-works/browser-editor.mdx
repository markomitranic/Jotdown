Click a word on a page in the studio and write. When you are done, a commit lands on the project's branch with your name on it, or, in a folder project, the file on your disk changes.

There is nothing to switch on and nothing to open. Every paragraph the server
rendered is already an editor, so a click puts a caret in it, and a bar appears at
the foot of the window as soon as the page says something different from the
file. That bar counts what you changed and saves it. The page's own title, icon and description are editable where the
reader sees them rather than in a header of their own: click the icon and a
search over the Lucide set opens, and the mark you pick shows up beside the
title and in the sidebar. There is no deploy to wait for in the studio: it reads
the branch head on every page view, so the next view of the page shows your
commit. A page left open notices a change made somewhere else, by an agent or
another machine, within a minute, and within ten seconds for a folder on your
own disk.

Without it, fixing one wrong word means opening the repository in an editor,
finding the file, editing markdown, committing and pushing. Nobody does that for
a typo, so the notes age.

## The editor was a second surface pretending to be the page

Until this version you clicked a pencil in the left margin, the article came off
the page, and a TipTap editor was put in its place: same column, same measure,
its own paragraphs, its own callouts, its own code blocks. It worked, and four
things were wrong with it. You had to ask before you could fix anything, and the
asking was a click most readers never made. The swap blinked, because replacing
a whole article in one render is not something a browser can be talked into
making look like nothing. Every block existed twice, once as the component that
draws it for a reader and once as the node view that draws it for a writer, and
the two had to be kept alike by hand. And the thing you wrote in was never the
thing anybody read, which is the one that bites: a callout a little off in the
editor was a callout nobody could check until after the save.

What replaced it is one page. ProseMirror renders its top node as the element it
is handed rather than one of its own, so an editor holding a document of words,
handed the `<p>` the server already rendered, puts that text straight back inside it.
Same tag, same classes, same place in the tree. There is nothing to swap, so
nothing moves and nothing blinks, and a click lands a caret exactly where it
looks like it should. A page is then not one editor but dozens of small ones,
which is why none of them keeps an undo stack of its own: they all report into
one record, so a single Cmd+Z undoes one thing however many of them it touched.

What lets a block be edited on its own is a stamp. `remarkSourceRange` writes
`data-src-range="12:1-16:4"` onto every top-level block as the page compiles,
naming the lines that block was written on, and on save the block splices its
new text into exactly those lines. Nothing re-prints the file around it.

The furniture that used to be a toolbar is in the margin and under the caret
instead. A six-dot grip beside every block copies, duplicates, deletes and drags
it, fences, tables, figures and dividers included, and the blocks inside a
callout have their own, so one can be dragged out of the box or another dragged
in. Its Turn into menu makes text, a heading, a list, a fence, a quote or a
callout into any other of those, keeping the words. A table or an image also
gets Width, Column, Wide or Full width, and a grip on its side to drag between
them; the width is written as a `:::wide` or `:::full` around the block, which
the editor takes off before the block's own editor sees it and puts back on
save. `/` opens a menu of every block there is. `- `, `1. `, `> `, `## `, ` ``` `
and `---` at the start of an empty line each turn it into the thing they look
like. Clicking a link opens a small popover with its address, and Visit, Edit
and Remove.

A selection inside one block is text, so half a sentence copies as half a
sentence. The moment a drag runs out of the block it started in, it becomes a
selection of whole blocks, each one tinted, the way Notion does it. Shift-click
selects every block between the caret and the click, Escape selects the block
the caret is in, and Shift with Up or Down at a block's edge takes in the one
beside it. Selected blocks answer Delete, Tab, which nests them in the list or
the box above, Shift-Tab, which takes them back out, and the grip, which drags
them all at once.

Copied or cut, they go on the clipboard as markdown, exactly as written, with
HTML beside it for a mail or a chat. Pasted back in the studio they arrive as
the same blocks, a fence still highlighted, and pasted into the middle of a
paragraph they break it in two around them. The grip copies one block as
markdown or as HTML too. Paste markdown, first in the `/` menu, reads anything
on the clipboard as markdown and turns it into blocks: a table arrives as a
table, a fence as a fence, a callout as a callout. A lone link pasted onto an
empty line of an `.mdx` page becomes a card with the page's title, description
and picture, read once by the studio and written into the tag, or a video for a
YouTube link; the grip's Turn into link takes it back when that was the wrong
guess. Pasted into a sentence, a link stays a link. Any other plain Cmd+V never
guesses.

Two things this costs, and the first is paid on every page. In the studio, the
editing chunk is fetched shortly after the article paints, on every page view,
because there is no click left to hang it on. The old model
loaded it when the pencil was clicked, so a reader who never edited never
downloaded it. That is the price of there being no click.

The second is narrower. A block the editor has no drawing for, a hand-drawn
figure, is left exactly as the server rendered it. It gets a
grip like any other block, so it can be copied, duplicated, deleted and dragged,
but there is nowhere to put a caret in it. Everything the slash menu can insert
is drawn by the editor whether it came from the file or from the menu: a fence
from the file is written in inside the very frame the server drew, a table opens
as cells, a `<Steps>` as its steps.

## Generated pages

Pages written by a tool should declare `generated: true` in front matter:

```yaml
---
title: Reference
generated: true
---
```

The page shows "generated" and "read-only" badges above its title. Browser
editing, metadata editing and deletion are disabled. The sidebar cannot rename
or move the page, or move a folder containing it. Copying and reading still work.

The save endpoints read the flag from the stored file. Removing it from a save
request or forcing a save does not bypass the restriction. A sidebar change
that would rewrite a link inside a generated page is also refused. Update the
source or generator in the repository instead.

A generator should write the flag into its output, and so should a release-log
tool that writes pages.

## The approach

Four pieces, each in one place.

A remark plugin, `remark-source-range.ts`, which stamps every top-level block
with the lines it was written on while the page compiles, so a block in the
browser knows which slice of the file is its own.

One
<abbr title="A rich-text editing framework built on ProseMirror. It gives you a document model and a schema, not a finished UI.">TipTap</abbr>
editor per block, mounted onto the element the article already drew.
`inplace/blocks.tsx` is the paragraph, the two lists and the quote,
`inplace/Heading.tsx` and `inplace/Callout.tsx` are the two shapes whose element
holds furniture the editor must not swallow, and `inplace/region.ts` is what
mounts any of them. Everything that floats over the article rather than living
in one block, the grip, the slash menu and the bar at the foot, hangs off
`inplace/context.tsx`. The selection menu is mounted beside the article.

A markdown bridge, `markdown/`, that turns file text into an editable document
and back again.

And the endpoints in `apps/studio/server/live-edit/`, `source.ts`, `save.ts`,
`structure.ts`, `asset.ts`, `history.ts` and `revision.ts`, all reached through
one route handler, `apps/studio/app/api/projects/[id]/live-edit/[action]/route.ts`. It runs
each request against the project named in its URL, as the studio's one editor:
whoever `git config --global` names, with the GitHub token you signed in
with. Every call to GitHub is made with your own token, and the studio keeps no
credential of its own.

There is nothing to set up per project and nobody to sign in, because the
studio runs on your own machine. The one gate in front of it all is `proxy.ts`,
which refuses any request that would change something unless it comes from the
studio's own pages: another website open in your browser can reach `localhost`
too. The conventions for writing the documents themselves are in the authoring
skill, [installed with the other docs skills](../context-warehouse/connecting-agents.mdx).

## A rich-text save would rewrite the whole file

The obvious build is to parse the markdown into a tree, edit the tree, and print
the tree back out. It works on the first try, and every save touches every line.
Bullets normalise from `*` to `-`, emphasis characters flip, blank lines move,
hard-wrapped prose reflows into one long line per paragraph. Fixing a typo
produces a three-hundred-line diff that no reviewer can read, and `git blame`
stops meaning anything.

So untouched blocks are never printed. At parse time each top-level block records
two things: the byte range it came from, and exactly how it prints today.

```ts title="apps/studio/src/plugins/live-edit/types.ts"
export type BlockOrigin = {
  /** Position among the original top-level blocks, for detecting deletions. */
  srcIndex: number | null;
  srcStart: number | null;
  srcEnd: number | null;
};
```

On save every block prints again. A block whose print still matches what it was
at parse time is *pristine*, and gets copied out of the original file rather than
printed. Runs of consecutive pristine blocks are copied as a single slice, so
whatever odd spacing sat between them comes along untouched.

```ts title="apps/studio/src/plugins/live-edit/markdown/serialize.ts"
while (i < nodes.length) {
  const from = pristineOrigin(parsed, nodes[i]);

  if (from === null) {
    pieces.push(printBlock(nodes[i]));
    i += 1;
    continue;
  }

  let to = from;
  let end = i + 1;
  while (end < nodes.length) {
    const next = pristineOrigin(parsed, nodes[end]);
    if (next === null || next.srcIndex !== to.srcIndex + 1) break;
    to = next;
    end += 1;
  }

  pieces.push(parsed.source.slice(from.srcStart, to.srcEnd));
  i = end;
}
```

Printing a block that did change takes one more step. Markdown reads a single
newline inside a paragraph as a space, so a hard-wrapped paragraph parses to one
long line and would print back as one, which turns a one-word fix into a diff
the size of the paragraph. `markdown/wrap.ts` fills the printed block back to
the column the file is wrapped at, measuring that column off the file rather
than assuming eighty, because a project that writes one sentence per line must
not be reflowed either. The words land where the author had them and the diff is
one line.

Frontmatter gets the same treatment, without a YAML library. Parsing and
re-emitting that block would reorder the keys and restyle every value, so
changing the title rewrites one line and leaves the rest of the header
byte-identical. The test suite parses the fixture pages that sit beside the
bridge, one of every block, a changelog a release tool wrote and a generated
reference, saves each with no edits, and asserts the output is identical to the
input.

## The editor has no idea what a DocCardList is

Our pages are MDX, not plain markdown. They hold JSX elements, inline SVG
figures, task lists, code fences carrying a meta string, and the odd import. A
rich-text editor has no shape for most of that, and inventing one would quietly
corrupt the page.

So the map from markdown to editor nodes is a short allowlist: paragraphs,
headings, both kinds of list, code fences, blockquotes, rules, images, tables,
callouts, and the seven Fumadocs tags the block list names. Anything else
returns null, and null at the top level becomes an
*inert block*: an atom holding the verbatim slice of the file, drawn greyed out,
selectable and deletable but never editable. On save it emits its source
unchanged.

```ts title="apps/studio/src/plugins/live-edit/markdown/toProseMirror.ts"
export function inertBlock(node: RootContent, source: string): JSONContent {
  const { srcStart, srcEnd } = nodeRange(node);
  return {
    type: "mdxBlock",
    attrs: { source: source.slice(srcStart, srcEnd), kind: inertKind(node) },
  };
}
```

## The menu offered blocks a .md page cannot render

Almost every page here is `.mdx`. A few are not: a page a generator wrote and
a [changelog](./changelog.md) are `.md`, because a release tool writes lines
like `fix: stop Promise<void> leaking` and MDX would read that as a component
and fail the page. Skipping the JSX parse is the whole point of the extension.

Which means JSX written into a `.md` file is not a component, it is six literal
characters. And until now the slash menu did not know that. Open the changelog,
press `/`, pick Video embed, and the editor cheerfully wrote `<VideoEmbed
url="…" />` into a file that renders it as text.

So a slash item that writes a tag now carries a flag, and the menu is built per
page:

```ts title="apps/studio/src/plugins/live-edit/inplace/slash.tsx"
export function inplaceChoices({ mdx }: SlashOptions, query: string): Item[] {
  const needle = query.trim().toLowerCase();

  return ITEMS.filter(
    (item) =>
      (mdx || !item.jsx) &&
      (needle === "" ||
        item.title.toLowerCase().includes(needle) ||
        item.keywords.some((keyword) => keyword.startsWith(needle))),
  );
}
```

`isMdx(path)` in `paths.ts` decides it, the page's provider in
`inplace/context.tsx` reads the path it already has, and `inplaceSlash({ mdx })`
hands it to the menu when a block mounts. Seven items carry the flag today:
Video embed, File attachment, Accordion, Steps, Tabs, Cards and File tree.
Everything else in the menu is
either plain markdown or a remark plugin, and callouts and mermaid fences both
render in `.md` for the same reason `remarkChangelog` does: the plugin builds
the component in the tree, so nothing has to be parsed out of the source.

## The file can change under you

An agent, your IDE or another machine can write the file you have open. The
thing that keeps a save from overwriting that is the
<abbr title="Git's content hash for one version of one file. GitHub returns it on read, and a save that names an out-of-date one is refused.">blob sha</abbr>,
and it is the check a save cannot skip.

A draft starts from the bytes this page rendered, and those carry no sha at
all, so one is fetched the moment you press Save. The file is read at the
branch head and taken only if it still reads exactly as the page in front of you
was rendered from. Anything else means something saved in between, and every stamp
on this page now points into a file that has moved underneath it, so the bar
says so and offers a reload rather than guessing. Your writing survives that:
the draft is kept in this browser against this page, replayed onto the newer
file when it loads, and anything that no longer has a place to go is held aside
for you to copy out. The sha from that read travels with the new text, and the
save endpoint checks it twice over. It reads the branch head, then the file's
sha at that head, and a sha that no longer matches is a 409. The commit itself,
GitHub's `createCommitOnBranch`, names the head it was checked against, so
GitHub refuses it if anything was committed in between, and the endpoint reads
and checks again, up to three times. A save that loses the race is refused
rather than silently overwriting the newer file.

A folder project has no branch to compare, so the check runs on the file
itself: the studio works out the blob sha from the bytes on disk, the save
writes only if it still matches, and anything else is the same 409.

folder on your disk, and refreshes the page when it has moved, unless you have
unsaved changes on it. GitHub answers an unchanged head without counting it
against your hourly limit, so an open tab costs nothing while nothing changes.

Names come from git. The studio has one editor, whoever `git config --global`
names on your machine, and the server hands that name and email to the page.
The commit is made with your GitHub token, so GitHub records the token's account
as the author, and a `Co-authored-by` trailer carries the name and email git
gave.

:::note

A publication, and the local preview that is one, has no editor at all. It is
built from its own app, which carries none of the editor's code, so a page
there renders as it would for any reader.

:::

## Ordering a page meant typing a number into it

Putting a page one slot higher in the sidebar used to mean opening that page,
finding a box called `Sidebar order`, and typing a number smaller than the page
above it. Then doing it again for every page underneath, because nothing stopped
two pages claiming the same number, and a tie was settled alphabetically without
telling anyone.

The sidebar is already on screen, so it became the control. In the studio every
row is something you can pick up, the way a page is in Notion: press anywhere on
it and move. There is no mode to switch on. Changes wait in a card at the foot
of the window until you press Save or Discard. A `⠿` grip shows
in the margin when you hover, and a small toolbar at the end of the row holds a
`+` for a page, separator or link inside it and a `⋯` for everything else. Order moved
into the folders at the same time: every folder has a `meta.json` whose `pages`
array names the things inside it, so a thing's place is its index and one drag
rewrites one line. `sidebar_position` is not used anywhere and is ignored if you
add one.

A drag can only reorder inside one list, and a page dragged from one section to
another crosses rows at three different levels. So the studio's sidebar is one
flat list rather than nested lists, with nesting drawn as a left pad of 12px per
level, which is the same step the reading sidebar indents by, so a publication
and the studio draw the same tree. Where a dragged row lands is two readings of the pointer: up and down picks the gap, and left and right
picks how deep in that gap, one level per 12px. A dashed slot sits in the list
at exactly that depth while you move, and the section it would land in lights
up, so what you see before letting go is what you get.

The neighbours set the limits, so a drag cannot make a shape the files cannot
have. A row goes no deeper than inside the section above it, since a
page cannot hold pages, and no shallower than the row below it, which would
otherwise be cut off from its own section. A shut section rested on for a moment
opens, so a page can travel anywhere in the tree in one drag, and a shut section
directly above the slot can be dropped into without opening at all. A folder
holding generated pages turns the slot red, and letting go there puts the row
back. `⋯ → Move to…` is still there for when the drag is fiddly.

A drop writes nothing. `projectDrop` in `structure/queue.ts` works out the gap
and the folder, and `dropOps` turns them into a `reorder` naming the destination
folder's new contents, plus a `move` when the row changed folders, and both join
the queue. The endpoint
takes the moved name out of the old folder's array itself, which is why a drop
that crosses sections is still two ops rather than three.

## A link was the one row you had to leave the browser for

The sidebar could always hold a link to another site. Fumadocs reads an entry
like `"[Next.js docs](https://nextjs.org/docs)"` in a `pages` array and draws it
as an ordinary row that happens to point off the site, and this site never had
to render anything for that to work. What it had no answer for was writing one.
The arranger drew such a row dead: no
grip, no menu, and any drag of the pages around it left the link pinned to the
index it started at.

The fix is smaller than it sounds, and the reason is that a link is not a file.
Every other change the arranger makes is arithmetic on a corpus of documents, so
creating a page is a write, moving one is a write and a delete, and deleting one
has to answer for the links pointing at it. A link is none of that. It is one
string in one `pages` array and nothing else exists.

So it rides in the op that already rewrites those arrays. A `reorder` names
every row in a folder, and it now names the links too, spelt exactly as the
`meta.json` spells them. That one change makes the order the whole truth about
that folder's links: a link the order leaves out is a link the reader deleted,
one it spells differently is one they re-pointed, and one that turns up in
another folder's order has moved there. Adding, editing, moving and deleting are
the same op, and `applyOps` on the server gained no case for any of them. What
it lost was a line: links used to be pinned in place alongside separators,
exclusions and extracted folders, and now only the last two are.

One thing had to be published for it to work. The page tree renders a link's
icon into a React element and keeps no record of how the entry was written, so
an order rebuilt from the tree alone would respell every link in it and quietly
drop the icons. The server now hands the browser those entries as written, keyed
by folder, next to the document index it already publishes for the same reason.

The last piece is a form rather than a field. Renaming anything else is one word
in one row, which is why it happens in the row. A link is three things, an
address among them, so it gets a dialog of its own rather than three fields a
row would hide most of the time.

## A group was a folder pretending to be a label

The sidebar used to offer a group beside a section: a folder with no landing
page, drawn as a label with its pages under it. A newcomer had to pick between
"a folder with a landing page" and "a label with pages under it" before writing
a word, and putting a page in a group moved its file, so its address changed
too. Groups are gone. The label is now a separator, and a separator is not a
folder at all.

A separator is one entry in a folder's `meta.json`, and Fumadocs draws it as a
label over every row after it, up to the next one:

```json title="docs/meta.json"
{
  "pages": ["index", "---[BookOpen]Guides---", "getting-started", "publishing", "..."]
}
```

That makes it the same kind of thing as a link, one string in one `pages` array,
so it rides in the same op. A `reorder` names separators spelt as written, the
order is the whole truth about them, and adding, renaming, re-iconing, dragging
and removing one are all a respelt order. `applyOps` on the server needed no case
of its own for any of it. **Add to the sidebar** and every page's `+` offer
Separator, which lands at the end of the folder, and you drag it to where it
should head.

A `meta.json` can still extract a folder, `"...runbooks"`, which draws that
folder's pages in its parent's list and throws the folder away. The browser is
then handed a flat run of pages whose files sit one folder down, and a drag
there would rewrite the wrong `meta.json`. `refold` in `structure/queue.ts`
folds each run back under one row for its folder, so its pages drag inside
their own order. The folder row itself stays pinned where its entry stands,
since moving it would mean respelling an entry the editor does not write.

## A page could not hold pages

A page that grew children had nowhere to put them. You had to decide up front
that something was a section, a folder with a landing page, and a page written
first could only get pages beside it. Notion has no such choice: every page can
hold pages, and the sidebar draws them all alike. The studio now works the same
way, and there is no "new section" anywhere in it.

Only a page that holds pages shows a chevron, at the end of its row, and one
without an icon of its own is drawn as a stack of pages, so an empty page and
a full one never look alike. Every page shows a `+` while the pointer is on it.
Name the first page, separator or link you put inside it, or drag a row in one
step to the right of it, and the queue stages a `nest` before it:

```txt
docs/setup.mdx  →  docs/setup/index.mdx
```

The page becomes the landing page of a folder named after it, so it keeps its
address, `/setup`, and its place in its parent's order, and the relative links
into and out of it are repaired like any move. The `nest` is never counted as
a change of its own, and undo takes it back with the first thing put inside. A folder with no landing page of its own, which a hand-written project
may still have, stays a plain group with its chevron always showing, and the
studio never makes a new one.

## An icon could only be changed in a file

A page's icon lives in its front matter, a section's in its `meta.json`, and a
link's or a separator's inside the entry itself, so the arranger had nothing to
click. Now `⋯ → Change icon…` opens the same Lucide picker a page title uses,
beside the row, and on a link or a separator the icon itself is the button. The change is an `icon` op in the queue like any other, and
the server writes it wherever that kind of row keeps its icon, and a link or a
separator is respelt with it. A page made in the browser starts with a plain
one, and a page without one is drawn with it, so every row lines up.

Whether a section starts unfolded was the same kind of file-only setting:
`"defaultOpen": true` in its `meta.json`. A section's `⋯` now carries
`Open by default` as a checkbox, staged as a `defaultOpen` op, and unticking it
takes the key away rather than writing `false`.

A folder with a `meta.json` and no `index.mdx`, a changelog split by major
version say, used to be drawn as a dead row: nothing in the page tree names its
folder. `refold` now reads the folder off the pages inside it, so it opens,
drags and takes pages like any section. One whose pages are generated still
keeps its order to itself.

## Where it all sits

The bridge in the middle is pure. `markdown/` takes a string and gives back a
string, with no DOM and no Node in it, which is why the tests can push a whole
page through it in milliseconds, in a runner with no browser anywhere near it.
Everything that knows about a browser sits above it, everything that holds a
credential sits below it, and the only file all three import is `types.ts`,
which imports nothing but types.

One boundary matters more than the rest. Every endpoint runs the
browser-supplied path through the same anchored allowlist, so an edit can only
reach an `.md` or `.mdx` file or a `meta.json` under `docs/`, and `next.config.ts`,
`proxy.ts` or `.github/workflows` are unreachable however the request dresses
them up. Nothing outside the content tree has a shape the allowlist accepts. In a
monorepo the server puts the project's folder in front of the path only after
the check, so the browser never names anything outside that project either.

```ts title="apps/studio/server/storage/github/editing.ts"
const CONTENT_PATH = new RegExp(
  `^${DOCS_ROOT}/(?:${PATH_SEGMENT}/)*${PATH_SEGMENT}\\.mdx?$`,
);
```

Every segment has to start with a letter or a digit, which makes `..` and
dotfiles unrepresentable rather than merely filtered. The raw string is what gets
tested, never a decoded one, so `%2e%2e/` fails on the `%`. The root is
interpolated rather than written out, so a renamed `docs/` cannot leave this
pointing at a folder that no longer exists. And `proxy.ts` carries no matcher,
so it covers `/api` as well as the pages: a write sent by another website is
refused before it reaches an endpoint, and every call that does reach GitHub
uses your token, so GitHub itself refuses anything your account may not do.
