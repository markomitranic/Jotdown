The context warehouse works best when `docs/` sits in the same checkout as the
code. Sometimes it cannot: your second brain lives in a repository of its own,
or one set of notes covers several projects. The agent then needs to be told
where the docs are and how to reach them, and the answer depends on what it
already has access to.

Say you are working in `you/site`, and the colour tokens it uses are written
up in your notes, `you/notes`. An agent asked why a button is the wrong colour
should read `notes/docs/tokens.mdx`, not guess. Three ways get it there, best
first.

## Clone it beside the code

A clone next to the checkout keeps `grep`, which is how an agent finds the page
it needs without knowing its name:

```sh
git clone git@github.com:you/notes.git ../notes
```

Then name the folder in the `AGENTS.md` paragraph of the repository the agent
works in:

```md
## Documentation

This site's docs live in docs/. My notes live in ../notes/docs/, cloned
beside this repository; pull it before reading. Grep both before answering a
question about how this site works.
```

## Read single files through `gh`

Without a clone, the agent reads one file at a time with the access its `gh`
login already has. Fine for a page it can name, poor for searching:

```sh
gh api repos/you/notes/contents/docs/tokens.mdx --jq .content | base64 -d
```

## Fetch the site

When the other docs are published as a site, the agent can read them over
HTTP, an index first and then any page as markdown. It works from anywhere, with no GitHub
access at all. See [Reading the docs over HTTP](./reading-over-http.mdx).

## Writing in the other repository

An agent that should also update the other repository's pages needs that
repository's skills, not this one's. Run the skills command at the root of the
repository it writes in, as in [Connecting your agents](./connecting-agents.mdx),
and commit there.
