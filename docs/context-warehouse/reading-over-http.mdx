An agent outside the repository reads your published site: `/llms.txt` lists
every page with its description, and every page is served again as its
markdown source. That is two `curl` calls from a question to an answer, with
nothing to install and no access to the repository.

Say you ask an agent in another project how refunds work in your side
project's checkout. It fetches the site's `/llms.txt`, sees "Refunds: how a
refund moves from request to bank", and fetches that page's twin. The answer
cites the page a reader of your site would read.

A site has no password of its own, so whatever it serves to readers it serves
to agents too. Private docs need access control at the host, and an agent
behind that control needs the same way in as you do.

## The two addresses

| URL | Returns |
| --- | --- |
| `/llms.txt` | Every page as a title, a link to its markdown twin and its description. Read this first. |
| `/markdown/<page>.md` | One page as the markdown it is written in, front matter included. The landing page is `/markdown/__root.md`. |

```sh
curl https://docs.example.com/llms.txt
curl https://docs.example.com/markdown/checkout/refunds.md
```

The index links to twins rather than HTML pages, so the second fetch lands on
source text. There is no search: the agent picks a page by its title and description.

## Why not the studio

The studio answers the same kind of addresses under each project, such as
`http://localhost:6192/you/notes/llms.txt`, plus a search at
`/you/notes/api/search?query=<words>`. It only does so on your own machine,
while it runs.

An agent does not need it. Everything the studio shows is a folder on your
disk or the head of a branch on GitHub, which the agent reads directly from a
checkout or with `gh`, as in
[Docs in another repository](./another-repository.mdx).
