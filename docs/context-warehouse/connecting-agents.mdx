An agent working on your code reads the documentation the way it reads the
code: as files in the checkout. That is the
<abbr title="The project's docs as plain files in its own repository, where an agent finds everything it needs before it touches the code.">context warehouse</abbr>,
the pages under `docs/`. There is no URL to configure, no server and no
password. Connecting an agent is two things: a paragraph in `AGENTS.md` that
says where the docs are and that they change with the code, and the skills
that teach it to write a page that renders.

Ask Claude Code in the checkout repository why a failed payment waits thirty
seconds before the retry. It greps `docs/` for "retry", opens
`docs/architecture/payments.mdx` and answers from the page you wrote.
Change the retry to ten seconds in the same session, and it updates that page
in the same commit.

## Tell the agent where the docs are

An agent opening a repository sees the code first, and in a monorepo the docs
may be at `apps/docs/docs/`. Say it once, in the file every session starts by
reading: `AGENTS.md` for Codex, Cursor, OpenCode and most others, and
`CLAUDE.md` for Claude Code, which can import the first with one `@AGENTS.md`
line. The setup wizard writes this section:

```md title="AGENTS.md"
## Documentation

This project's documentation lives in `apps/docs/docs`, written with Jotdown,
and is updated in the same change as the code it describes. Before writing or
editing a page, run `npx skills add markomitranic/Jotdown --skill '*' -y` to
refresh the docs skills, then read `.agents/skills/authoring/SKILL.md`. To
review a page before committing, open the project in Jotdown.
```

Reading needs nothing more. Every page carries a `title` and a one-sentence
`description` in its front matter, so `grep -r "^description:" docs/` is a
table of contents the agent builds for itself.

## Give it the skills

Writing a page that renders takes house rules: which blocks exist, that props
are literal values, how uploads are addressed, how a figure is drawn. They
ship as
<abbr title="A folder with a SKILL.md an agent loads when a task matches its description, so the instructions are there only when needed.">skills</abbr>,
fetched with the [`skills` CLI](https://github.com/vercel-labs/skills) (1.7,
September 2026):

```sh
npx skills add markomitranic/Jotdown --skill '*' -y
```

That command does three things:

- copies every Jotdown skill into `.agents/skills/`, where Codex, OpenCode and
  most other agents look for them;
- links each file into `.claude/skills/` for Claude Code, one symlink per file
  rather than per folder, since pnpm cannot install a git repository that
  holds a symlink to a folder;
- records what it fetched in `skills-lock.json`.

Commit all three, so an agent on a fresh clone or another machine has the
skills before it ever runs the command. The paragraph above has the agent rerun it before each docs
task, so a skill that changed in Jotdown arrives as an ordinary diff in your
next commit. The skills are authoring, blocks, chart, figure and
editorial-illustration; each says when it applies, and the agent loads one
only when the task matches.

### Illustrations in your project's colours

Every page opens with an illustration, and the editorial-illustration skill
has the agent paint it. It reads the article, picks the one idea a reader
should feel, and draws it as a scene with a small impossibility in it. The
result is one SVG file in the project's uploads, holding the day and the night
palette both, and the page shows it as an ordinary image on its first line. A
page stays a page to read, for you and for an agent, rather than a few hundred
kilobytes of path data with the prose underneath.

The style is the same in every project; the colours are not. The agent starts
from the `theme` in `.jotdown/config.json` and moves away from it only where
the scene's mood asks for it, so a project in greens gets plates in greens. It
paints the dark mode as the same scene at night rather than inverting the
day. The colours are fixed when the page is written: change the theme later,
and existing plates keep theirs until an agent repaints them.

## Keep the docs current

The line that matters most is "updated in the same change as the code it
describes". An agent that changes behaviour a page describes rewrites the
page in the same commit, so the docs move with the code instead of a quarter
behind it. Review those pages like the code beside them; see
[Reviewing a page an agent wrote](./reviewing-agent-pages.mdx).

    An
    <abbr title="Model Context Protocol: a standard way for an agent to connect to a server, ask which tools it offers, and call them mid-task.">MCP</abbr>
    server for the docs would offer three tools: list the pages, read one,
    search. An agent already has all three as `ls`, `cat` and `grep` on files
    in its checkout, faster and with no process to run. For docs elsewhere, a
    site answers with two URLs and a `curl`; see
    [Reading the docs over HTTP](./reading-over-http.mdx). The one thing MCP
    adds is appearing in the tool list without the `AGENTS.md` paragraph, and
    that paragraph also tells the agent to keep the pages current, which no
    tool list would.
