Your pages can use blocks the framework does not ship. A hero for your landing page, a pricing table, a list of the latest guides: write it once as a React component in `.jotdown/components`, put `<Hero />` on a page, and the site draws it. Open the page in Jotdown through your site and the hero's title is a line you click and type into, the prose between its tags edits like any paragraph, and `/` offers a fresh one.

Say your notes need a landing page. You write `Hero.tsx`, a layout called `landing`, and a page whose front matter says `layout: landing`. The published site draws the page without the docs sidebar, the hero across the top. In the app you change the tagline where it stands, press save, and the file gets one changed attribute, nothing else.

Two folders hold all of it, `.jotdown/components` for blocks and `.jotdown/layouts` for layouts, both committed with your content. They are code, so they run in your site's build and in its [editing canvas](./publishing.mdx), and never in the app itself. A page still holds no code: it only names the blocks, with plain text props, the way it names a callout.

## Writing a block

A block is a component exported from a file in `.jotdown/components`, and its export name is the tag a page writes. One file can export several.

```tsx title=".jotdown/components/Hero.tsx"
import type { ReactNode } from "react";
import { Editable, Slot } from "@jotdown/kit";

type Props = { title?: string; tagline?: string; children?: ReactNode };

export function Hero({ title, tagline, children }: Props) {
  return (
    <section className="not-prose my-10 rounded-2xl bg-primary/5 p-10">
      <Editable.Text prop="title" value={title} as="h2" className="block text-4xl font-semibold" />
      <Editable.Text prop="tagline" value={tagline} as="p" className="mt-3 block text-muted-foreground" />
      <Slot className="prose mt-6">{children}</Slot>
    </section>
  );
}
```

```mdx title="docs/index.mdx"
<Hero title="Notes that publish themselves" tagline="Write in place, publish on every push.">

Everything here is a file in git.

</Hero>
```

Style it with Tailwind and the theme's tokens, `bg-primary/5`, `text-muted-foreground`, so it follows your [theme](../studio/branding.mdx) in both modes. A block named like one of ours, `Callout` or `Cards`, replaces ours on every page. Markdown itself, paragraphs, headings and lists, is the framework's and only styled.

Props arrive as strings, since a page may only write literal values. Turn `limit="6"` into a number inside the component.

## Making it editable

What a block draws through the kit's primitives is what the canvas lets you change:

- `Editable.Text` is one line of a prop. It is plain text on the site, and in the canvas a line you click and type into, written back into the tag when you leave it.
- `Editable.Image` is a picture whose address is a prop. In the canvas it offers **Replace picture**, which uploads the file you pick and writes its address.
- `Slot` is where the prose between the tags goes. Each paragraph in it edits like any other on the page, and an empty slot offers a first line to type.

Every block also gets a grip, so it moves, copies and deletes like any block, and **Settings…** in the grip's menu edits its source. Register it with `defineBlock` and the settings become a field per prop, and `/` offers it by name:

```tsx
import { defineBlock } from "@jotdown/kit";

export const Hero = defineBlock(HeroBlock, {
  title: "Hero",
  description: "A big title, a tagline and a picture",
  props: { title: { default: "A new idea" }, tagline: { default: "Say it in one line" }, image: { kind: "image" } },
  children: "Tell the reader why it matters.",
});
```

## Reading the site from a block

A block can ask where it stands. `usePage()` is the page's title, description, address and front matter, `useSite()` the site's title and address, and `usePages({ folder: "guides", limit: 6 })` the pages of a folder in the sidebar's order, which is all a "Read next" grid needs. Link between pages with the kit's `Link`, which in the canvas opens the page in the app.

`useInStudio()` says whether the page is drawn inside the studio rather than for a reader, so a block or a layout can leave out what only readers want while you edit: analytics, a cookie banner, a video that plays on its own. It is true on every page the studio draws, while `useIsEditable()` is true only where a block can be edited in place:

```tsx title=".jotdown/components/Analytics.tsx"
import { useInStudio } from "@jotdown/kit";

export function Analytics() {
  if (useInStudio()) return null;
  return <script defer src="https://plausible.io/js/script.js" data-domain="notes.example.com" />;
}
```

## Giving a page a layout of its own

A page is drawn in the docs shell, with the sidebar and the table of contents, unless its front matter names another layout:

```yaml
---
title: Welcome
description: The front door.
layout: landing
---
```

`blank` is the page and nothing around it. Any other name is a file in `.jotdown/layouts`, whose default export gets the page, the site and the page's content to place:

```tsx title=".jotdown/layouts/landing.tsx"
import { Link, type LayoutProps } from "@jotdown/kit";

export default function Landing({ site, children }: LayoutProps) {
  return (
    <div className="min-h-dvh">
      <header className="mx-auto max-w-5xl px-6 py-5">
        <Link href="/" className="font-semibold">{site.title}</Link>
      </header>
      <main className="prose mx-auto max-w-5xl px-6">{children}</main>
    </div>
  );
}
```

To change the layout of every page that names none, set `"layout"` in `.jotdown/config.json`.

In the canvas a block's root is placed by your layout exactly as on the site, so a grid of blocks spanning its columns with `col-span-2` lays out the same while you edit. Put the span on the block itself, as a class or an attribute it styles: the studio keeps a boxless element around each block, which a child selector like `.bento > [data-cols]` can't see through.

### Drawing the page's title

A layout that draws its own heading gets the page's title and description through `Editable.Title` and `Editable.Description`. On the site they are plain text. In the canvas they are written back into the page's front matter, and an empty description still shows, so it can be written:

```tsx title=".jotdown/layouts/post.tsx"
import { Editable, type LayoutProps } from "@jotdown/kit";

export default function Post({ children }: LayoutProps) {
  return (
    <article className="prose mx-auto max-w-2xl py-16">
      <Editable.Title className="text-4xl" />
      <Editable.Description className="lead" />
      {children}
    </article>
  );
}
```

`as` picks the tag, `h1` and `p` unless you say otherwise.

### A layout for a whole folder

Every post of a blog wants the same layout, and a post written in the app should get it without anyone typing `layout: post`. Name it once in the folder's `meta.json`:

```json title="docs/blog/meta.json"
{ "title": "Writing", "layout": "post" }
```

A page takes its own front matter's layout first, then the nearest folder's above it, then the config's. Nothing is written into the pages, so moving a page into the folder gives it the layout, and moving it out takes it away.

### Wide and full blocks in your layout

A picture or a table set to wide or full stands wider than the column, measured against the main area. In the docs shell that is the space between the sidebar and the table of contents. In your layout it is the window, which is right for a column centred on the page and wrong for one beside a sidebar. Say how wide your main area is with `--jd-main-width` on the column:

```css
.post-column { --jd-main-width: calc(100% + 4rem); --jd-bleed: 0px; }
```

`100%` is the column itself, so wide and full read as the column. `--jd-bleed` is how far full stops short of the main area's edges, `1.5rem` unless you set it, and `--jd-wide-width` caps wide, `75rem` unless you set it. The width grips in the canvas follow the same values.

## Starting from ours

`jotdown add block` lists the blocks the framework can hand you, and `jotdown add block Hero` copies one into `.jotdown/components` to change as you like. `jotdown add layout landing` does the same for a layout. A file you already have is never overwritten.

## Seeing it while you work

Choose **Dev server** in the renderer menu on the status strip along the bottom of the app, and the app starts your site's dev server and edits the project through it. Save a component and the page in front of you redraws with it. **Publication** edits through the published site, so it draws your blocks as they were last deployed, and **Skinny** is the app's own look, where a block of yours is a labelled stand-in you can still move.
