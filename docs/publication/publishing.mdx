A
<abbr title="The read-only website built from one project's docs for its readers, with no editor in it.">site</abbr>
is one project built into static files, hosted on anything that serves files:
GitHub Pages, Vercel, a bucket behind a CDN. The repository stays content:
`docs/`, its uploads included, and a `.jotdown/config.json` that names the
Jotdown version to build with. On every push the host clones Jotdown at that
version beside the content, runs its build script, and serves the files that
come out. Nothing is committed back.

The build writes every page, markdown twin, upload and search index once, so
the site needs no server, no secret and no sign-in, and carries none of the
<abbr title="The app on your own machine where you read and edit every project">studio</abbr>'s
editing code. Why it is built this way is in
[ADR 0018](../decision-records/0018-publication-is-its-own-app.mdx).

## Set up a site

<Steps>
<Step>

### Keep the repository to content

It holds `docs/` with its uploads, `.jotdown/config.json` and the agents'
skills. No `package.json`, no lockfile, no framework code. A project the setup
wizard made is already like this.

</Step>
<Step>

### Say where it is hosted, and pin the Jotdown version

`url` is the site's address, and a site hosted below a domain's root, like a
GitHub Pages project site, is built under that path. Every build clones the
tag or branch `jotdown` names, `main` when unset:

```json title=".jotdown/config.json"
{
  "jotdown": "v0.3.1",
  "title": "Notes",
  "url": "https://you.github.io/notes"
}
```

A release's own tag freezes the site on it until you bump it by hand, and
`main` takes unreleased work on the next deploy.

</Step>
<Step>

### Deploy it

[On GitHub Pages](./github-pages.mdx) is one workflow file and a setting.
[On Vercel](./vercel.mdx) is two files and a project setting. Anywhere else,
`.jotdown/out` is the site: copy it to whatever serves files.

</Step>
<Step>

### Push and check

The build log prints `Jotdown commit:`, then the link check. A broken link or
a page that does not compile stops the build, and the last good deployment
keeps serving. Once it is live, open a page with an image, `/llms.txt`,
`/markdown/__root.md`, and one old address from `docs/moved.json`.

</Step>
</Steps>

A save to a GitHub project in the studio is a commit like any other push, so
it starts a new deploy. A save to a folder is not, until you commit and push
it yourself.

## What a site serves

- **Every page** at its address: `docs/onboarding/first-week.mdx` is
  `/onboarding/first-week`.
- **A markdown twin per page** at `/markdown/<page>.md`, and `/llms.txt`
  listing them all, for agents. See
  [Reading the docs over HTTP](../context-warehouse/reading-over-http.mdx).
- **Uploads** at `/uploads/…`, `/img/…`, `/files/…` and `/whiteboards/…`,
  from the project's uploads folder.
- **Search**, opened with ⌘ K or Ctrl K. Each section's text is written
  during the build and searched in the reader's browser.
- **A forwarding page** at every old address in `docs/moved.json`, which sends
  the reader on to where the page lives now.

There is no editor. Search engines are turned away by `robots.txt` and a meta
tag on every page.

<Accordions>
  <Accordion title="Look at a site before you push">
    From a checkout of Jotdown, point `jotdown` at the project folder. `dev`
    serves the site and rebuilds a page as its file changes; `build` writes
    the files a host would get into the project's `.jotdown/out`:

    ```sh
    bun scripts/jotdown.ts dev ~/Sites/notes
    bun scripts/jotdown.ts build ~/Sites/notes
    ```

    `bun run check:links ~/Sites/notes` runs the link check on its own.
  </Accordion>
</Accordions>
