A
<abbr title="The read-only website built from one project's docs for its readers, with no editor in it.">site</abbr>
is one project built into a Next.js app and deployed on Vercel. The repository
stays content: `docs/`, its uploads included, and a `.jotdown/config.json` that
names the Jotdown version to build with. On every push Vercel clones Jotdown at
that version beside the content, runs its build script, and deploys the app
that comes out. Nothing is committed back.

Each page, markdown twin and search section is written once, on its first
visit, and Vercel serves it from its CDN after that. The uploads are copied in
during the build. The site carries none of the
<abbr title="The app on your own machine where you read and edit every project">studio</abbr>'s
editing code. Pictures go through Next's image optimizer, which hands each
reader a WebP copy sized to their screen. Why it is built this way is in
[ADR 0018](../decision-records/0018-publication-is-its-own-app.mdx) and
[ADR 0027](../decision-records/0027-a-site-is-a-nextjs-app-on-vercel.mdx).

## Set up a site

<Steps>
<Step>

### Keep the repository to content

It holds `docs/` with its uploads, `.jotdown/config.json` and the agents'
skills. No `package.json`, no lockfile, no framework code. A project the setup
wizard made is already like this.

</Step>
<Step>

### Say where it is hosted, and pin the Jotdown version

`url` is the site's address, which the studio hands out as the link to a page.
Every build clones the tag or branch `jotdown` names, `main` when unset:

```json title=".jotdown/config.json"
{
  "jotdown": "v0.3.1",
  "title": "Notes",
  "url": "https://notes.vercel.app"
}
```

A release's own tag freezes the site on it until you bump it by hand, and
`main` takes unreleased work on the next deploy.

</Step>
<Step>

### Deploy it

[On Vercel](./vercel.mdx) is two files in `.jotdown/` and a project whose
root directory is `.jotdown`.

</Step>
<Step>

### Push and check

The build log prints `Jotdown commit:`, then the link check. A broken link
stops the build, and the last good deployment keeps serving. A page that does
not compile shows the error page until it is fixed. Once it is live, open a page with an image, `/llms.txt`,
`/markdown/__root.md`, and one old address from `docs/moved.json`.

</Step>
</Steps>

A save to a GitHub project in the studio is a commit like any other push, so
it starts a new deploy. A save to a folder is not, until you commit and push
it yourself.

## What a site serves

- **Every page** at its address: `docs/onboarding/first-week.mdx` is
  `/onboarding/first-week`.
- **A markdown twin per page** at `/markdown/<page>.md`, and `/llms.txt`
  listing them all, for agents. See
  [Reading the docs over HTTP](../context-warehouse/reading-over-http.mdx).
- **Uploads** at `/uploads/…`, `/img/…`, `/files/…` and `/whiteboards/…`,
  from the project's uploads folder.
- **Pictures** through `/_next/image`, scaled to the reader's screen. The
  original stays at its own address for the download button.
- **Search**, opened with ⌘ K or Ctrl K. Each section's text is written
  once and searched in the reader's browser.
- **A permanent redirect** from every old address in `docs/moved.json` to
  where the page lives now.

There is no editor. Search engines are turned away by `robots.txt` and a meta
tag on every page.

<Accordions>
  <Accordion title="Look at a site before you push">
    From a checkout of Jotdown, point `jotdown dev` at the project folder. It
    serves the site and rebuilds a page as its file changes. A branch you push
    gets its own preview deployment on Vercel.

    ```sh
    bun scripts/jotdown.ts dev ~/Sites/notes
    ```

    `bun run check:links ~/Sites/notes` runs the link check on its own.
  </Accordion>
</Accordions>
