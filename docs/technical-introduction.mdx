![An open paper folder stands on a desk beside a laptop full of code, and the shadow it throws on the sunlit wall is not a folder but an easel, a globe on its stand and a robot reading a page.](/img/docs/illustration-technical-introduction.svg "Your repository holds one folder of pages beside the code, and the studio, the site and the agents are all just shapes that folder casts.")

Jotdown is three ways of reading one folder of markdown. The folder lives in
your repository, next to whatever it describes, and Jotdown itself is never
copied into it: the studio reads the folder from disk or GitHub, a site build
clones Jotdown beside it, and an agent reads it straight off the disk. Your
repository carries content and one config file, and nothing in it runs code.

Take a side project with a checkout service. Its pages sit in `docs/` beside
`src/`, so Claude Code greps them while it works on the payment flow. Readers
open `docs.checkout.example.com`, built from the same files on every push. And
when you spot a wrong timeout, you fix it in the studio, where the save is a
commit on the branch under your own git name.

## The stack

Jotdown is [Fumadocs 16](https://fumadocs.dev) on Next.js 16, App Router and
Tailwind CSS v4, run with Bun 1.4.2. It is one repository with three
workspaces:

| Workspace | What it is |
| --- | --- |
| `packages/core` | The renderer: compiling a project, the blocks, the page, the shell, the theme, search. Both apps build it. |
| `apps/studio` | The studio: the editor and every project you open, running on your own machine. |
| `apps/publication` | One project at the site root, read-only, built wherever you host it. |

The two apps are whole Next.js apps that never import each other. Whatever only
the studio does lives only in the studio, so a site carries no editing code and
needs no GitHub at runtime. See
[ADR 0018](./decision-records/0018-publication-is-its-own-app.mdx).

## A content project

```
<repository>/
├── .jotdown/
│   ├── config.json     ← title, branch, content folder, theme, Jotdown version
│   └── vercel.json …   ← the host's files, once it is published
└── <content>/          ← the repository root unless config.json names another
    └── docs/           ← every page, a meta.json per folder, moved.json
        └── _uploads/   ← images, files, whiteboards, fonts
```

`.jotdown/config.json` is plain JSON and every field is optional; a repository
appears in the studio once the file exists. In a monorepo, `content` points at
the folder holding `docs/`, such as `apps/docs`. Every field is in
[Configuration](./how-it-works/configuration.mdx), and every file under `docs/`
in [Pages and folders](./how-it-works/pages-and-folders.mdx).

## A page is content, never code

Pages are MDX, but only the markdown half of it. A page may use the
framework's fixed set of blocks, callouts, figures, tabs, steps, embeds, with
literal props, and nothing else: an `import`, an `{expression}`, a `<script>`
or an `on*` handler fails the page before it compiles. That is what lets the
studio open any repository without trusting it, and lets a host build a site
without auditing the content. The studio and a site compile a page through the
same remark chain in the core, so a page reads the same in both.

[Every block](./examples/every-block.mdx) is one worked example of each block
there is.

## The studio

The studio runs on your machine and serves every project you open at
`/<owner>/<repo>/<page>`. There is one editor, you: the name and email that
`git config --global` holds go on every save. GitHub is read and written with
the token you signed in with, kept in the Keychain, so the studio can only show
and change what GitHub already lets you.

- **A folder.** Pages are read from disk, and a save writes the file and
  commits nothing. You review it with `git diff` like any other change.
- **A GitHub repository.** The studio copies the content at the branch head
  into a scratch folder, compiles it, and checks the head again every minute.
  A save is one commit on the branch, checked against the file's version so it
  never overwrites a newer one.

There is no database anywhere: git, or the folder, is the store for pages. How
the editor turns a rendered page back into markdown is in
[The browser editor](./how-it-works/browser-editor.mdx).

## The site

A site build clones Jotdown at the version `.jotdown/config.json` pins, next to
the content, and runs its build script. Every page, its markdown twin and every
upload are rendered once, `docs/moved.json` becomes redirects, and the link
check stops the build on a broken link. The result is a Next.js app that serves
your readers and holds nothing it would need to fetch. A site has no password
of its own, so private notes need access control at the host.

## The context warehouse

The context warehouse is not a deployment at all: it is the `docs/` folder, read
by an agent with `ls`, `grep` and `cat`. What Jotdown adds is the know-how to
write pages that render, shipped as agent skills that a content project
installs with the [`skills` CLI](https://github.com/vercel-labs/skills) and
refreshes before each docs task.
